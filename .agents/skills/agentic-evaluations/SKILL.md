# Agentic evaluations

Evaluate LearnUnlock Tutor/specialist prompts, tool descriptions, and agent behavior against this stable skill. Invoke manually with a case ID, training subset, training suite, or held-out checkpoint. With no selection, show at most four proposed training cases for approval. Do not run a case until the user approves its exact version. Each new or revised case needs approval; approval of the skill does not approve cases. Grok is the intended inexpensive runner; any available coding agent can execute this protocol. Record the actual agent/model rather than claiming Grok ran.

Temporary user preference (October 9, 2026): run agent evals locally to save OpenRouter Sol credits. Use the local development app with Dev auth and ChatGPT sign-in for the existing Sol 6.1 specialists; keep Gemini on OpenRouter. Confirm local Sol routing before starting. If local credentials or required renderer services are unavailable, report the blocked setup instead of switching to production or paid OpenRouter Sol. Production runs require an explicit user request. Record the actual app URL and environment; label local live evidence separately from production evidence.

## 1. Prepare

Read `manifest.json`. Show at most four cases in each approval round. Record the case ID, version, exact approved opening, and the user approval in the attempt inputs. Draft and pending cases cannot run. Then read ONLY the selected `students/<id>.json`. Create an immutable attempt directory under `output/agentic/<run-id>/`. Record skill/rubric/scenario versions, actual student/reviewer identities, app URL and environment, exact start and end timestamps in ISO 8601 UTC with seconds and milliseconds, the local IANA time zone, local Git commit, deployed commit if visible (otherwise `unknown`), app version if visible (otherwise `unknown`), and baseline run if any. Preserve first attempts and retries separately. Capture each Study Session and message time when available; label the time source as captured or app-displayed. Never reconstruct exact times from dates or file modification times. A local commit is not proof of the deployed commit. Include the exact run times in generated reports, the combined full-chat cover, and the chart gallery. Preserve the native session export bytes unchanged.

Alternate case attempts continuously between mobile and desktop across invocations, including one-case runs and retries. Start a new evaluation sequence on mobile. Read `deviceSequence` in the manifest and the latest attempt inputs; use the next device, rather than restarting on mobile for each invocation. Before simulation starts, record the device assignment and advance the sequence to the other device. An unstarted case does not advance it. Record `startingDevice` in the run results. Manifest case `device` values are historical/default suggestions; the sequence determines this attempt’s device. Keep the same device within a multi-session case. Even-sized batches have equal numbers on each device; odd-sized batches continue the sequence next time. Use a 390 × 844 CSS-pixel mobile viewport and a 1440 × 900 desktop viewport. Verify and record the actual dimensions before the first student message. Pass this assignment explicitly to student and reviewer agents. This tests responsive layouts, not physical touch hardware. Restore the previous viewport after the run.

Use the preferred browser available to the runner: Codex in-app Browser in Codex. LearnUnlock production is `https://www.learnunlock.app`; sign-in and synthetic credentials are documented in `.agents/context/TESTING.md#agent-sign-in`. Keep credentials out of reports and screenshots. Use ordinary UI paths and normal usage limits. Local runs use the verified loopback app URL; the production URL applies only to explicitly requested production runs. A limit or browser failure ends the attempt as blocked/incomplete with evidence; it is not a Tutor failure.

Inventory prior evaluation-created state through the UI. Capture pending evidence before deleting only clearly identified evaluation sessions/plans. Keep unrelated saved work. Record persistent learner state that cannot be reset; mark affected checks unable to verify. Open a fresh Study Session for the case; use an evaluation-specific title when editing is available.

Complete when the selected role file, attempt directory, identities, and initial state are recorded. Held-out cases are selected explicitly; normal invocations stay on training.

## 2. Simulate the student

Prefer a separate student subagent with a fresh context. Supply only this phase, the selected student JSON, sign-in instructions, evidence output directory, and capture contract below. The student must not receive reviewer rubrics, expected checks, implementation files, or other scenarios. If subagents are unavailable, read the student role now and defer review-file loading until the final student interaction is captured. Record `sequential-weaker-isolation` for that fallback; instructions to defer reading do not provide context isolation.

Send `opening` exactly. Treat `privateContext` as hidden student knowledge. Disclose only one requested detail when the Tutor asks a relevant question. Do not volunteer the exam, deadline, exact problem/data, or prior knowledge. Be adversarial through natural low effort, incomplete answers, occasional wrong confidence, and mild pushback. Do not deliberately help the Tutor discover every requirement. Direct answers requested by the student remain valid Tutor behavior. Follow the persona's known prerequisites, confusion, confidence, conditional behaviors, and return instructions. Respond to the Tutor within that script. Most replies use 2–8 words. Answer only one part of a multi-part question. Sometimes omit requested work, give a number alone, say idk, or forget. Adapt after useful help. Do not systematically comply with every instruction. Occasional longer replies need a natural reason. Preserve misconceptions until relevant teaching repairs them. When struggling, admit the specific confusion; do not coach the Tutor toward an expected tool or hidden checklist. Explicit visual requests appear only in scenarios labeled `explicit`.

Operate learner-visible controls before describing their effect. Capture initial and meaningfully altered visual states. Review plan proposals as this student: confirm accurate ones, edit incorrect editable fields or ask for correction, and inspect saved state after confirmation. Keep the same plan throughout a multi-session case. Create new Study Sessions at natural breaks as the role prescribes. Same-day production returns establish persistence/reorientation, not simulated days; do not change system dates or claim real spaced-retention evidence.

Capture every ordered student and Tutor message in full, including visible math text and all readable visible tool-call labels/details. Capture proposals and decisions, saved-plan before/after states, relevant URLs, screenshots, loading/errors, and action outcomes. Put each screenshot alongside a caption and the associated turn. For graph-creation/link findings, show the Tutor message containing the graph link or Artifact chip, with its surrounding explanation. A later view of the open graph proves rendered content only; it does not show where the Tutor linked it. Capture the creation/link context and a separate graph detail view when both are needed. Use native export if available; keep a neutral JSON transcript too. If native export is unavailable, capture visible text for the reporting tool. Screenshots preserve mathematical notation and visuals when plain-text capture loses layout. Mark omitted or unreadable content explicitly; never label a partial capture complete.

Student handoff format: `transcript.json` with `sessions:[{id,url,captureComplete,messages:[{role:"student"|"tutor",text,screenshots:[{path,caption}]}]}]`, plus neutral `events` with turn references, plan decisions, visible tool observations, saved-state observations, interruptions, and capture gaps. Paths are relative to the attempt directory. The student records facts and does not score.

Complete when the activity ends naturally within the role's total student-message bounds, all Study Sessions and evidence are saved, and the student context is finished. At a cap mid-activity, mark incomplete. Do not delete state before exports and review.

## 3. Review after simulation

Only now read `review/rubric.md` and the selected case entry in `review/cases.json`. Review the complete chat, screenshots, all meaningful visual interactions, visible tool calls, and confirmed plan state. Use a separate reviewer context when available. Inspect only app-visible information; private traces, database queries, source, network payloads, and internal reasoning are outside the evaluation evidence contract.

Apply every common and case-specific check. The detailed rubric is the standard; there are no answer keys. Identify obvious incorrect calculations, contradictions, geometry, or scientific claims. If correctness or tool route cannot be established visibly, record unable to verify. A displayed graph does not prove which hidden tool parameter was used.

For every check, record binary or event-count results, evidence references, and a short rationale. For rates, maintain an opportunity ledger with each eligible event, expected change, actual result, and success/failure. A 4/6 result means four observed successes from six eligible events, never a subjective fractional grade. Cases with no eligible events are not applicable. Include incorrect/unnecessary proposals separately.

Produce `results.json` following `references/report-format.md`. Include all expected check IDs; missing evidence becomes unable to verify. Write `evaluation.pdf` with the short evaluation and score charts. Write complete native chat exports to a separate `full-chats.pdf`. Discuss evaluator behavior and execution limitations in the invoking chat; retain detailed capture records in JSON.

Use ASD-STE-style short, active sentences. Present Minus, Plus, then Interesting. Select up to ten most relevant failures, fewer when fewer are observed. Rank them by impact and recurrence; give supporting app-feature failures high priority when they block use, lose work, or prevent review. Put them in the Auxiliary failures subsection of Minus, each with its own M reference, screenshot, and precise captured record. Each displayed finding requires screenshot evidence of the actual event; a later student reaction alone is insufficient. Capture transient proposals before accepting or dismissing them. For each low event score, state the counting unit and success rule. Explain whether failures repeat one issue or represent distinct issues. Show representative failures from each distinct category as separate Minus findings, with the proposed value, the student work that was available, the missing evidence, and screenshots of the actual proposal. Add a short Failure context paragraph directly after Minus to explain the score’s counting rule, repeated versus distinct failures, and material limitations. Include the full event ledger in the detailed records. Select at most three Plus findings. Place screenshots and records beside their P, M, or I reference. Keep the short evaluation below 1,000 words; full chat exports have no word cap. Separate evaluator coverage misses from Tutor failures in the chat. Keep repair methods and timings in raw records.

Obtain and verify the actual app-exported PDFs before appending them to `full-chats.pdf`. If the browser cancels a generated download, repair capture using `references/export-capture.md`. Preserve original native PDFs unchanged in the attempt evidence directory. A reconstructed transcript is supplemental evidence. Record unresolved export failures in the chat and detailed records, with screenshot evidence when available.
## 4. Generate and display

Run `bun .agents/skills/agentic-evaluations/scripts/report/cli.mjs <attempt>/results.json --out <attempt>/report`. Add `--baseline <prior>/results.json` only for compatible evaluator, skill, rubric, and scenario versions. The command validates counts and screenshot evidence, computes scores and 80% Wilson intervals, exports charts, and creates a report folder containing `evaluation.pdf`, separate `full-chats.pdf`, results/computed JSON, chart gallery, and an `assets/` evidence folder. Skill version 6 and later use separate chat exports; set `reportFormat: "separate-chat-exports"` to reformat earlier results without claiming a new run. Set `summary.minusContext` to the short Failure context paragraph. The generated `manifest.json` records the PDF renderer version, source commit, modified-source status and source hashes; a commit alone cannot identify uncommitted renderer edits. Native session exports follow case order in `full-chats.pdf`. Generated text uses bundled Lexend fonts. Python with ReportLab is needed; use `--python <bundled-python-path>` when needed.

Render and inspect all generated report pages. Verify readable screenshots, math, charts, section order, and complete separate chat exports. Open/display `evaluation.pdf`, `full-chats.pdf`, and the chart gallery. Label screenshot captions with the case, device, and turn. Show both mobile and desktop evidence for a batch that ran both devices. Capture the actual tested viewport; resizing a mobile screenshot cannot supply desktop evidence. State the actual run scope and device counts in the chat. For a one-case run, state its device and the next device in the sequence. Outputs stay gitignored under `output/`.

The gallery intentionally offers multiple views so the user can select the most useful charts. Training and held-out panels remain separate. Retries and incomplete attempts do not replace complete first attempts. Wilson intervals for repeated events in one conversation are approximate because observations are correlated. Small case counts cannot establish broad reliability. Unknown checks never silently become successes.

## Iteration

Freeze skill, rubric, and scenario versions during product prompt/tool iterations. Change tester instructions only as a separate calibration step with a new version. Preserve resolved inputs for every attempt. Once held-out evidence informs a change, move that case to development/training and replace it with a fresh concept/misconception case before the next protected checkpoint. A changed app version alone does not invalidate comparison; changing the evaluator or test contract does.

Delete only evaluation-created state after complete exports if a reset is requested or the next independent case requires it. Preserve multi-session state within cases. Local controlled-time testing is a follow-up in GitHub issue #53; this skill does not require it.
